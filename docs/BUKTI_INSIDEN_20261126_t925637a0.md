## 1. Ringkasan (untuk owner)

1. **PoolTimeout bukan Postgres mati.** Postgres sehat (`pg_stat_activity` 34/100 koneksi, probe DB 1,6 s, `db.available=true`). Timeout berasal dari **event loop `fund2-alerts` yang beku** saat membaca file tick harian 95 MB + 111 MB secara sinkron (`paper/feed.py:read_ticks`) di dalam coroutine. Terukur 16,7 s per panggilan; di host yang sedang swap + load 5, membeku sampai **>300 s**.
2. **Semua watcher lain ikut mati waktu.** `ea_watch`, `paper_watch`, `sev_watch` menunggu koneksi pada loop yang sama; deadline acquire 10 s habis selagi loop tak bisa jalan, maka `psycopg_pool` melempar `PoolTimeout: couldn't get a connection after 10.00 sec` walau pool kosong. Sudah direproduksi terisolasi (5 waiter + 1 `read_ticks` → 5× PoolTimeout identik, DB idle).
3. **Halt = efek samping watcher SEV.** `metrics.collect_metrics` menangkap PoolTimeout itu sebagai `db.available=False` → SEV-2 `db_unavailable` → kill-switch `STOP_NEW_ORDERS`. Event 224 (01:22:04), 226 (01:44:19), 228 (02:17:54) semuanya dari jalur ini.
4. **`fund2-alerts` kini rusak total**: restart tiap ~5m15s (STALE exit 70 → systemd restart), `NRestarts=12`, 5 siklus berturut-turut 02:04:47 → 02:27:00. Artinya notifikasi kill-switch/EA-offline **tidak andal** dan halt palsu bisa terpicu lagi kapan saja.
5. **Status trading aman**: 0 posisi terbuka (250 CLOSED), mismatch rekonsiliasi 0, order macet 0. Perbaikan permanen ada di kode `app/alerts.py` + `paper/feed.py` = kartu `hf-backend` (sudah dibuat, P1). Sampai itu mendarat, **melepas halt akan diikuti halt palsu berikutnya dalam hitungan menit**.

### 3.3 Mengapa muncul `PoolTimeout` padahal DB sehat

`psycopg_pool.pool_async.getconn()` menghitung `deadline = monotonic() + timeout`
(10 s, `DEFAULT_ACQUIRE_TIMEOUT_S`) lalu `if timeout <= 0: raise PoolTimeout()`.
Kalau event loop beku 16–300 s, deadline semua penunggu sudah lewat saat loop
kembali, sehingga **semua** langsung melempar `PoolTimeout` tanpa pernah
menyentuh Postgres.

Reproduksi terisolasi (pool `min_size=1, max_size=10, timeout=10`, identik
`app/db.py`), 5 task akuisisi + 1 task `read_ticks` sinkron:

```
total: 15.44 s
  0 -> PoolTimeout: couldn't get a connection after 10.00 sec  (15.43 s)
  1 -> PoolTimeout: couldn't get a connection after 10.00 sec  (15.43 s)
  2 -> PoolTimeout: couldn't get a connection after 10.00 sec  (15.43 s)
  3 -> PoolTimeout: couldn't get a connection after 10.00 sec  (15.43 s)
  4 -> PoolTimeout: couldn't get a connection after 10.00 sec  (15.43 s)
```

String error identik dengan `kill_switch_events.reason` 224/226/228, sementara
Postgres dalam keadaan idle.

Lalu di `metrics.collect_metrics()` (baris 620–677) exception apa pun dari
`db.pool().connection()` diubah menjadi `db.available=False`, dan
`evaluate_sev()` (baris 719) memetakan itu ke **SEV-2 `db_unavailable`** dengan
auto-action `STOP_NEW_ORDERS`. `sev_watch_loop` hanya berjalan di
`fund2-alerts` (`main.py` API tidak punya sev loop), jadi **setiap halt
`auto:sev_db_unavailable` berasal dari daemon alerts**.

### 3.5 Mitigasi

**Permanen (milik hf-backend, kartu P1 dibuat dari kartu ini):**
1. `feed.read_ticks()` wajib off-loop: `await asyncio.to_thread(feed.read_ticks, ...)` atau jadikan `read_ticks_async`. Satu perubahan ini menghapus pembekuan event loop.
2. Baca **ekor** file, bukan seluruh file: buka dengan `seek` ke ~8 MB terakhir (atau baca terbalik baris demi baris sampai `ts_utc < cutoff`). Biaya jadi konstan, tidak tumbuh sepanjang hari.
3. `collect_metrics()`/`evaluate_sev()`: `db.available` jangan disimpulkan dari `PoolTimeout` saat loop stall, probe dengan timeout pendek (mis. 2 s) dan bedakan `PoolTimeout` (indikasi event loop) dari `OperationalError` koneksi (DB benar-benar down), supaya SEV-2 `db_unavailable` tidak menjadi auto-halt palsu.
4. Turunkan `ALERTS_STALE_TIMEOUT_S` atau pindahkan `beat()` agar tidak bergantung pada iterasi watcher (opsional, pertahanan berlapis).

**Operasional (sudah/akan dilakukan):**
- `fund2-candle-rollup` dinyalakan (lihat §5).
- Kartu terpisah untuk host hygiene (8 unit restart-loop sisa migrasi native), dampak ke latensi fund2 nyata, tapi di luar scope kartu ini dan menyentuh produk lain.
- **Tidak ada** perubahan yang melepas halt; halt tetap `STOP_NEW_ORDERS` aktif (event 228).
